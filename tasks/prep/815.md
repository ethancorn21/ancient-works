## 2. Plan

### P1. The fix (acceptance box 1, first half)

`web/index.html:1136`, in `addPairMarker` (function 1134-1139; the marker line is 1136, as
the task file says):

```js
function addPairMarker(p) {
  const el = document.createElement('div'); el.className = 'gpin'; el.textContent = P.pairs.length;
  const m = new maplibregl.Marker({ element: el, draggable: true }).setLngLat([p.lon, p.lat]).addTo(map);
  m.on('dragend', () => { const ll = m.getLngLat(); p.lon = ll.lng; p.lat = ll.lat; refit(); });
  P.marks.push(m);
}
```

becomes (option added, one house-style why-comment):

```js
function addPairMarker(p) {
  const el = document.createElement('div'); el.className = 'gpin'; el.textContent = P.pairs.length;
  // subpixel: the vendored Marker default (false) rounds _pos to whole pixels on every
  // setLngLat and moveend update, so the handles jitter 1 px on each drag, toolbar
  // scale/turn and re-emission - pass true so they track the true projected point (815)
  const m = new maplibregl.Marker({ element: el, draggable: true, subpixelPositioning: true }).setLngLat([p.lon, p.lat]).addTo(map);
  m.on('dragend', () => { const ll = m.getLngLat(); p.lon = ll.lng; p.lat = ll.lat; refit(); });
  P.marks.push(m);
}
```

Why one place is enough (all checked this session): every pair marker on the page - the
owner's initial click-placed pins and ALL re-emitted corners/centre - is created through
this one function. Callers: `map.on('click')` (index.html:1144, initial placement),
`web/fitkit.js` `_fkApply` (219; full rebuild after any pair-count change - triggered by
every s+/r+ toolbar step via `_fkScheduleApply`, 455) and `_fkActivate` (549; marker
seeding at 578 in the place chain: 4 corner handles + the hidden centre);
`_fkReemitLive` (201) only moves existing markers with `setLngLat` - exactly the update
path the vendor rounds. No other `new maplibregl.Marker(` exists outside the vendor
(grep of web/ this session: only index.html:513, :1136, :1255).

Vendor ground truth (checked this session in web/vendor/maplibre-gl-5.6.0.js; minified,
one line - grep the snippets):
- Marker ctor: `this._subpixelPositioning = e && e.subpixelPositioning || !1` (default false)
- Marker's public setter (what 816's probe uses): `setSubpixelPositioning(e){ return this._subpixelPositioning = e, this }`
- `_update` tail: `this._subpixelPositioning || e && "moveend" !== e.type || (this._pos =
  this._pos.round()); n.setTransform(this._element, `${anchor} translate(${this._pos.x}px,
  ${this._pos.y}px) ...)` => rounding happens on event-less updates (`setLngLat`, `addTo`)
  and on `moveend`; 'move'-type updates keep subpixel; `subpixelPositioning: true` disables
  rounding everywhere. (The OTHER `setSubpixelPositioning` / `subpixelPositioning:!1` hits
  in the vendor belong to the Popup class - leave them alone.)

Idempotency with the probe (why the owner check passes UNCHANGED - box 1, second half):
the probe's `subpixel()` guards with `if (!m._subpixelPositioning)` - with the page fix
already true, the setter call is skipped; the forced `m.setLngLat(m.getLngLat())` re-runs
`_update`, which no longer rounds, so the marker lands at the SAME fractional `_pos` a
born-subpixel marker has (both project the same lngLat after the same settled camera).
Same `_pos` => same inline transform => same pixels. The 816 recipe's own comment already
promises this: "Idempotent with the page-side fix (addPairMarker passing
subpixelPositioning: true)".
