### 3.1 `fit/review.py` + `data/review/` — the item format, upsert, export (boxes 1, 3, 4)

Stdlib-only module (importable by 203a/203b/212) + CLI `python3 fit/review.py export [--root DIR]`.

**Item file — one per site** (`data/review/<site>.<lead-plan>.json`; `<lead>` = `candidates[0].plan`, matching
the platefit doc naming `<site>.<plan>`; when the item has no candidates — "no picture found" — the file is
`data/review/<site>.json`). Contract (this is what 203a/203b/212 write and 201's README states):

```json
{
  "site": "alligator-effigy-mound-q4732645",
  "candidates": [
    { "plan": "ancientmonuments00squi_n0214_2",
      "title": "\"The Alligator,\" Licking county, Ohio",
      "url": "books/ancientmonuments00squi/n0214.jpg",
      "evidence": { "…200's field, verbatim, only when the source row has one…" },
      "pairs": [[u, v, lon, lat], "..."],
      "coarse": true,
      "…producer extras, pass-through: 202's ground/scale_m_px/rot_deg/scale_source/note,
       203a's gate_score/why, and the row's ia/file/book/label/cite/map_box/view/size when known…" }
  ],
  "no_picture_found": null,
  "resolved": null
}
```

Rules: `site`, `candidates` required (empty list for the no-picture variant, then `no_picture_found:
{"searched": "<what was searched>", "at": "<iso>"}` required); per candidate `plan`, `title`, `url`
required; `url` is **exactly what the page's `openPlan` loads** (`books/<ia>/<file>` for book rows,
`media/commons/<site>/<hash>.jpg` for commons rows); `pairs` in platefit-doc format (page px of the
candidate's image frame → lon/lat; 1dp px / 7dp lon-lat, as the docs store them) and **optional** (a
could-not-fit item may carry 0-3 model pairs, or none); `resolved` = `{"doc": "<site>.<plan>", "at":
"<iso>"}` once any of the item's candidates is fitted — **never cleared, never overwritten by an upsert**.

API (the contract 203a's prep already assumes):

```python
def item_path(root, site_id, lead=None) -> str            # <site>.<lead>.json or <site>.json
def upsert_item(root, site_id, entries, no_picture=None)  # merge candidates by `plan`; never clears
                                                         # `resolved`; never writes web/data/review.json
def candidate_evidence(plan_id) -> dict | None            # index.jsonl by id; files.jsonl by
                                                         # c_+sha1(title)[:16] (full 1381-row scan,
                                                         # once per run; §2 has why)
def resolved_doc(item, root) -> str | None                # item["resolved"]["doc"], else any existing
                                                         # data/db/platefits/<site>.<c.plan>.json
def export(root) -> (n_open, n_total)                     # writes web/data/review.json, records resolved
def main(argv)                                            # subcommand `export`, option --root
```

- **Resolution is derived, never a second store** (R4): an item is OPEN iff `resolved` is null AND no
  `data/db/platefits/<site>.<plan>.json` exists for ANY of its candidate plan ids (saving one candidate's
  pairs resolves the whole item — box 3: "saving resolves the item"). When `export` finds a doc, it writes
  `resolved: {doc, at: <the doc's at>}` back into the item file (the "saved doc id recorded" of box 3).
- **Export** writes `web/data/review.json`: `{"at": <iso>, "items": [ {site, name, lead, candidates
  (as in the item, verbatim), no_picture_found}, … ]}` — **open items only**, sorted by site name; `name`
  joined from `web/data/sites.json` (a site missing from it falls back to the raw id — log, don't fail).
  The page's count is `items.length` — computed, never hardcoded (box 4). Merging by the item's `site`
  field (not the file name) makes per-(site,plan) files and per-site files coexist, if 203a's first
  implementation drifts.

- **R1 — headless boot of the full page (the real blocker risk).** Unverified whether MapLibre boots under

  Outcomes: (a) boots → case 2 as written. (b) `pageerror` kills boot → the box-6 "shows the item in the
  review list" degrades to case 4's data-level assertion + the served review.json, logged in DECISIONS and
  filed as `## Proposed changes` on 201 if a page-level check is deemed required. The page itself works in
  a real browser either way.
- **R2 — shot.mjs needs Google Chrome, absent here.** Machine change, session 1: `cd /tmp && npx -y
  playwright@1.63.0 install --with-deps chrome` (AGENTS-legal: the library's own pinned downloader; lands
  at `/opt/google/chrome/chrome`; record the exact commands + version in PITFALLS so the VM stays

  node script using the bundled chromium-1243 (same evaluate, same assertions — a deviation from the
  box's literal tooling, noted in DECISIONS).
- **R3 — CODEMAP rule vs box 5.** The architecture rule says index.html takes "exactly one change (201's
  script tag)"; box 5 additionally mandates the `loadPlans` keying fix (pre-agreed in PLAN assumption 8).
  The task file wins; if the driver's re-check complains, it is answered with a DECISIONS entry citing
  PLAN 8 + box 5, not by 201 editing the architect's rule.
- **R4 — who records the resolution, and when the page "catches up".** The page cannot write `data/review/`
  (outside the web root; serve.py is not 201's file). Design: resolution is DERIVED (platefit doc exists →
  item resolved) and written into the item file by the next `export` (212 at project end); the page
  updates its own list/count in-memory + localStorage immediately after a save. Consequence: a page re-opened
  before the next export shows the just-saved item again as open — acceptable: box 3's "resolves the item"
  is met by the doc + `resolved` record, which case 3 checks; box 4's count is what 212 finally syncs.
  Alternatives (page PUTs a `review/` db collection; serve.py after_write hook) both add state or touch a
  file outside 201's Touches — rejected, noted here so the 201 agent doesn't re-derive them.
- **R5 — item granularity.** One file per site (chosen; matches the goal and the doc naming) vs one per
  rejected (site, plan) (a naive 203a loop). The export merges by the `site` field, so both granularities
  work; the README tells 203a to use `upsert_item` (one per site). If 203a's merged module drifts, 203a's
  own R6 says the merged `fit/review.py` wins — so ship the API clean and stable.
- **R6 — candidate row missing from plans.json** (212 stages a new picture and adds its row later; or a
  row lists a since-removed site — 230/1166 rows reference missing site ids, 203b's pitfall). review.js
  synthesizes the row from the candidate's stored fields (§3.2.4); the page fits on the loaded image's
  actual size, so if the recorded `size` frame differs from what loads, the pre-placed pairs may be
  slightly off — the human drags; note in the candidate's `note` when that can happen.
- **R7 — pre-placing pairs vs openPlan's crop** (from the old prep, still holds): 202's pairs are
  full-image px; `map_box` only shades the canvas, so pre-placed points outside the crop still show; book
  rows with `map_box: null` crop to the whole page. Never snap (fitkit/plan_fit invariant).
