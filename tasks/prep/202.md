## 3. Plan (mapped to the acceptance boxes)

`fit/propose.py`, one job per function: readers (`index_row(plan_id)`, `site(sid)`, `plans_row(plan_id)`) →
`parse_scale(text, row) -> (m_per_px, source) | None` → `anchor(...) -> proposal dict` → `propose_for(
site_id, plan_id) -> dict` → CLI.

- **Scale, three-way (boxes 1-2)**: (a) **bar**: `scale_bar` box present + tick-list/total text parses →
  `span_m / bar_box_width_px` (span = last tick − first tick in the unit: ft 0.3048, yd 0.9144, mi 1609.344,
  ch 20.1168, pace 0.762 (assumed 0.5 yd — flag it), no unit → None; "N ft" without ticks = total span).
  Self-contained, no ppi. (b) **ratio text**: `N units per printed inch` → `N·unit_m / BOOK_PPI[book]`
  (ppi table from summary.md + the three working-phase lookups; "or 1:1800" style: the printed ratio wins,
  1800·0.0254/ppi; `1/32m` = 1/32 mile per inch). Unknown ppi → (c). (c) **coarse** (box 2): scale =
  `max(size_m)/max(map_box px)` (for a no-LiDAR site this is the aerial's own 1 m/px of the site box —
  genuinely useful; for LiDAR sites it is just a guess — fine, `coarse: true`, "the human drag is expected
  to do the work"); `view: true` rows: same, plus `note: "perspective picture: similarity is a seed only"`.
- **Rotation (boxes 1-2)**: the §2 rule (hint if trustworthy, else 0; keep the hint in `note` either way).
  North-up both plate and ground (fitkit: relief and aerial are north-up) → no extra term.
- **Centre (boxes 1-3)**: map-panel centre (`map_box` centre in the `size` frame; page centre if absent) →
  the site centre `(lon, lat)` from sites.json. Transform: `z = a·(w−w0)+z0`, `a = (m_per_px /
  ground_scale(lat)) · e^{iθ}` (Mercator metres per page px; exactly the shape `similarity()` inverts).
- **Pairs (boxes 1-3)**: 4 panel corners + 1 extra (panel centre when `map_box` present, else page centre)
  → 3-5 pairs `[[u, v, lon, lat]]`, u/v in the `size` frame (1 dp, as docs store), lon/lat **7 dp** (fitkit
  `save()` convention). For `view`/coarse rows: same shape, `coarse: true`. Never snapped, never more than
  the panel: the pairs a human drags are the drawn frame's corners (the visible straight features of a
  stage-B plan), so a re-crop or drag of one corner is one small move, not a re-placement (R4).
- **Output dict** (201 stores it verbatim): `{"pairs": [...], "coarse": bool, "ground": "relief"|"aerial"
  (from sites.json: `lidar === false` → aerial, else relief — the fitkit convention), "scale_m_px": round
  4dp, "rot_deg": round 2dp, "scale_source": "bar"|"ratio"|"picture_size"|null, "note": str|null}`.
  Deterministic (no timestamps).

## 5. Risks and open questions (not asked of the human during prep)

- **R1 — fudge's row**: S&D "Plate XXXIII No. 2 (surveyed by James M…)" has no obvious index match
  (n0203/n0223 are Kentucky/Indiana/South Carolina works). Session 1: grep the S&D lists (`data/books/lists/

  box's parenthetical names the *ground*, not exactly six pairs; five + a note is acceptable; six is
  preferred if found.
- **R2 — imports**: `plan_fit` imports numpy and **PIL at module top** (PIL unused by `similarity`); the
  .venv is broken per PROGRESS. Session 1: `python3 -c "import numpy, PIL, pytest"` — if PIL is missing,
  the test must not import `plan_fit` bare: either install nothing and use a 12-line in-test copy of the
  same complex LSQ (marked "must track plan_fit.similarity") or log a DECISIONS note requesting the driver's
  venv fix. `fit/propose.py` itself stays import-safe with **stdlib only** (no numpy: the anchor is two
  lines of complex arithmetic) — that keeps the batch (203a/b) able to run it in any environment.
- **R3 — the scale-text grammar is the riskiest code**: OCR truncation ("Scale of Fee[t]"), bare numbers
  ("1000 ft", "500 feet" — total span, not ticks), units paces/chains/miles-with-fractions ("0 1/2 1 mile"),
  missing unit ("0 1/4 1/2"), the "or 1:1800" double statement, word numbers ("one mile", "forty feet").
  Design: closed grammar, table-driven, **fail → None → coarse** (never a wrong scale; a wrong scale anchor
  is worse than a coarse one — it would make the human's drag converge to the wrong size). Pace length:
  0.5 yd is a common surveying pace; flag the assumption in the module docstring and `note`.
- **R4 — "pairs on drawn features (plan corners, straight lines)" without reading the image**: hermetic tests
  + data/raw gitignored + "no texture search (the bet that failed)" all rule out Hough/ink analysis in 202.
  Resolution: for stage-B plan rows the recorded `map_box` *is* the drawn frame (a straight-line rectangle a
  human sees in a second); corners + centre are the pairs. If a reviewer insists on wall points, the upgrade
  is a later Qwen piece-label pass (the autofit oracle pattern) — out of scope, log if pressed.
- **R5 — "25 hand fits" reconciled** (PLAN.md: "25 fitted drawings, 19 of them from 20 documents"): 19 sites
  from the 20 docs (old-sarum twice) + 6 old-style site.json fits = 25. The test's regression guard covers
  all 25 (20 doc sha256s + 6 site.json fit hashes) — cheap, and it is the one thing that must never move.
- **R6 — the 90° class (measured, decided)**: a single corner-distance tolerance cannot pass: 3 of 9 indexed
  hand fits are drawn rotated 75-90° while the (only) rotation hint says 0/None (aztalan, maiden-castle,
  old-sarum). The three-way sanity check of §4-case-2 is the design decision; if session 1's measured Δrot
  for those three lands outside [75°,105°] (e.g. 74.96 vs the 75° edge), widen the band to [70°,110°]
  before pinning — the band's job is "a human notices the plate is turned and drags one corner", not
  "the proposal is rotationally exact". Never loosen (a)/(c) to make a site pass: those are the honest
  quality bars of the scale-bar anchor.
- **R7 — consumer contract**: 201 (parallel, wave 1) may already have a candidate shape; 203a/b (wave 2/3)
  will import `propose_for`. Keep the signature `propose_for(site_id: str, plan_id: str) -> dict` and the
  dict keys stable, and state both in the module docstring first. If 201 shipped different key names,
  203a reconciles at its start (its prep notes define the item shape; 201's notes say pairs+coarse).
